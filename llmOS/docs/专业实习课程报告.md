## 摘要

随着大语言模型（LLM）在在线服务中的规模化部署，推理成本瓶颈已从单次算子性能转移到显存管理、请求调度与数据搬运等系统层面。LLM 推理的 KV Cache 具有“按序列增长、可共享、可换出”的特征，与操作系统中的分页内存、写时复制、进程调度、虚拟内存高度同构。本报告以操作系统视角重新审视大模型推理，设计并实现了一套名为 llmOS 的推理操作系统原型：以离散事件时钟统一驱动 KV 内存管理、批处理调度、分层预取与 GPU 虚拟化四个子系统，通过冻结的接口契约与统一的请求状态机串联成一条完整的推理路径，并构建了包含 13 组对照实验的量化评测台与可视化界面。

实验结果表明：分页式 KV 管理将 OOM 率由 45.45% 降至 0，峰值并发由 2 提升至 6；持续批处理使吞吐提升 17.1%，首 token 延迟下降 35.4%；公平调度使跨租户 P99 方差下降 85%，吞吐仅损失 0.9%；分层预取将 DMA 停顿占比由 93.5% 降至 81.7%，有效算力占比由 6.5% 提升至 18.3%；GPU 超卖在保持越界拦截率 100% 的前提下获得 2.5 倍租户密度。全部结果在固定随机种子与黄金 trace 下可复现，自动化测试 46 项全部通过，覆盖率 93.27%。此外，借助本地部署的 Qwen2.5-0.5B 完成了真实 GPU 上的方向性背书，验证了仿真结论与真实引擎在方向上的一致性。

**关键词**：大模型推理；操作系统；KV Cache 分页；连续批处理；异步预取；GPU 虚拟化

## ABSTRACT

With the large-scale deployment of Large Language Models (LLMs) in online services, the cost bottleneck of inference systems has shifted from single-operator performance to system-level concerns such as memory management, request scheduling, and data movement. The KV Cache grows per sequence, can be shared, and can be swapped out, which is highly isomorphic to paging, copy-on-write, process scheduling, and virtual memory in operating systems. This report re-examines LLM inference from an OS perspective and implements a prototype inference operating system named llmOS: a discrete-event clock uniformly drives four subsystems — KV memory management, batching and scheduling, hierarchical prefetching, and GPU virtualization — connected into a complete inference path through frozen interface contracts and a unified request state machine. A quantitative evaluation bench with 13 controlled experiments and a visualization console is also built.

Results show that paged KV management reduces the OOM ratio from 45.45% to 0 and raises peak concurrency from 2 to 6; continuous batching improves throughput by 17.1% and reduces TTFT by 35.4%; fair scheduling reduces cross-tenant P99 variance by 85% at a throughput cost of only 0.9%; hierarchical prefetching lowers the DMA stall ratio from 93.5% to 81.7% and raises effective compute utilization from 6.5% to 18.3%; GPU oversubscription achieves 2.5× tenant density while keeping the isolation-violation interception rate at 100%. All results are reproducible under a fixed random seed and a golden trace, with 46 automated tests passing and 93.27% statement coverage. A locally deployed Qwen2.5-0.5B further provides a real-GPU directional backing consistent with the simulation.

**Key words**: Large Language Model Inference; Operating System; KV Cache Paging; Continuous Batching; Asynchronous Prefetching; GPU Virtualization

## 1. 引言

### 1.1 编写目的

本文档是计算机科学与技术专业实习（A 类：系统设计类）的课程报告，面向“面向大模型推理优化的操作系统级任务”选题，覆盖概要设计、详细设计、系统实现与系统测试四个阶段的工作。文档的读者包括指导教师、评审专家以及后续接手该代码库的同学。

编写本文档的具体目的有三点：其一，说明我们为什么用操作系统的概念与方法去处理大模型推理问题，以及这种映射在哪些环节成立、在哪些环节存在边界；其二，给出四个子系统的设计决策、接口契约与关键实现，使读者能够在不阅读全部源码的前提下理解系统结构；其三，用可复现的实验数据回答“这些机制究竟带来多少收益、代价是什么”，而不是停留在定性描述。

与一般课程设计报告不同，本项目的交付物不是单一程序，而是“仿真内核 + 评测台 + 实验数据 + 复现脚本”的组合。因此本文档在描述实现的同时，也记录了实验配置、冻结参数、失败案例与返工过程，以便评审复核。

### 1.2 项目背景

大模型推理的成本结构正在发生变化。以自回归生成为例，每生成一个 token 都需要对历史上下文做一次注意力计算，历史键值（KV Cache）随序列长度线性增长。在 4K 上下文、多并发场景下，KV Cache 的显存占用往往超过模型权重本身，成为限制并发数的第一因素。与此同时，在线请求长度高度不均，静态批处理会让短请求等待长请求，造成 GPU 空转；权重分层加载带来的 DMA 停顿又会进一步侵蚀有效算力。

这些问题在操作系统课程中都有对应物：显存碎片对应外部碎片，KV 块的共享对应写时复制，请求排队对应进程调度，分层预取对应按需调页与预读，多租户隔离对应地址空间保护与配额。因此，本项目不追求实现一个新的推理引擎，而是把操作系统机制抽取出来，在可控的仿真环境中做定量验证，回答“这些机制在 LLM 负载下能带来多少收益、代价是什么、在什么条件下成立”。

项目由课程任务书给定，要求四个子系统共享同一时钟、一条请求穿过完整 OS 路径，并在冻结配置下完成至少四组必做对照实验。既有系统方面，工业界的 vLLM 已通过 PagedAttention 与连续批处理解决了其中一部分问题，我们的工作以其为参照系而非替代品：不修改、不集成 vLLM，仅在其机制层面做可控实验，并用一次真实 GPU 对照提供方向性背书。

## 2. 总体设计

### 2.1 设计目标

系统设计目标按功能、性能、可用性、安全性、可扩展性五个维度给出，且全部可度量、可验证：

| 维度 | 目标 | 度量方式 |
| --- | --- | --- |
| 功能 | 一条请求依次经过调度、配额、VMM、KV 分页，四个子系统共享同一时钟 | 端到端实验 E1/E4/E7/E9 均可运行并输出完整指标 |
| 性能 | 分页相对连续预占 OOM 率下降；持续批相对静态批吞吐上升；预取相对串行 stall 下降 | 同一 seed 下 A/B 对照，指标方向必须成立 |
| 可用性 | 固定 seed 下结果逐位一致；黄金 trace 指标波动不超过 1% | 重复运行与回归测试 |
| 安全性 | 越界访问拦截率 100%，隔离违规率 0；超额申请被拒绝 | E8/E9 与单元测试 |
| 可扩展 | 新增实验只需注册配置，不改内核；新增租户不改调度代码 | 代码审查与模块依赖检查 |
| 工程质量 | 自动化测试覆盖率不低于 70%，README 一键复现 | pytest + coverage 门禁 |

### 2.2 设计原则

1. **分层与依赖单向**：接口层（HTTP/前端）只依赖实验编排层，编排层只依赖内核接口，内核内部四个子系统互不直接引用实现，只依赖冻结契约。
2. **模块化与高内聚**：KV 内存、调度、预取、虚拟化分属四个目录，各自的配置、数据结构与测试独立；跨模块改动必须走交叉评审。
3. **契约冻结**：接口签名、异常语义、配置常数在项目开始时冻结，任何变更必须同步修订文档并重跑黄金 trace，保证 A/B 对比公平。
4. **单一代价函数**：静态批与持续批共用同一个请求推进函数与同一套 prefill/decode 代价模型，禁止出现“两套模型各算各的”。
5. **确定性优先**：所有随机只来自 `random.Random(seed)`；所有等待表示为事件堆中的完成时刻，禁止真实 sleep 与线程调度依赖。
6. **可观测**：每个实验输出 baseline 与 optimized 两份完整指标、图表数据与配置摘要，界面与报告只引用这些结构化产物。

### 2.4 系统架构

系统采用“单时钟 + 四子系统 + 冻结契约”的事件驱动架构，自上而下分为四层：

1. **展示与接口层**：Vue 3 评测台与 FastAPI 服务。服务暴露实验目录、运行、历史记录、真机背书四组接口；前端负责实验选择、结果可视化与历史回放。
2. **实验编排层**：每个实验是一个配置对象，声明负载、基线构造、优化构造与指标归集方式；运行后统一产出 baseline/optimized 指标、图表数据与甘特数据。
3. **内核层**：KV 内存管理、批处理调度、分层预取、GPU 虚拟化四个子系统，通过冻结接口协作，共享同一请求状态机（WAITING/RUNNING/PREEMPTED/FINISHED）。
4. **基础设施层**：离散事件时钟（最小堆）、合成负载生成器、离线 trace 加载器、配置与确定性随机源。

主要数据流为：请求到达 → 配额准入 → 调度器排队 → KV 块分配与页表映射 → 每拍前向（预取 stall 计入本拍）→ 完成释放；显存不足时触发换出或抛出 `AllocError`，越界访问抛出 `IsolationError`，配额超限抛出 `QuotaOOM`，三者均由调度器显式捕获并记录。

```text
[Vue 评测台] ──HTTP──> [FastAPI] ──> [实验编排]
                                      │
                     ┌────────────────┼────────────────┐
                     ▼                ▼                ▼
              [调度子系统]      [KV 内存子系统]    [预取子系统]
                     │                │                │
                     └────────┬───────┴────────┬───────┘
                              ▼                ▼
                       [GPU 虚拟化/配额]   [离散事件时钟]
```

## 3. 场景项目

### 3.1 场景描述

场景设定为一个多租户在线推理服务：两个租户共享一张 GPU，租户 alpha 承载交互式对话，对首 token 延迟敏感；租户 beta 承载批量摘要，对吞吐敏感。服务在同一个模型、同一张卡上同时接受两类请求，需要在不相互拖垮的前提下尽可能提高整体利用率。该场景刻意选择了“延迟敏感 + 吞吐敏感”这一最常见的混合负载形态，因为它能同时暴露静态批处理的空泡问题、连续批处理的公平问题、显存分配的碎片问题以及权重加载的停顿问题。

#### 3.1.1 背景及国内外现状

**（1）行业背景。** 大模型应用的重心已从训练转向推理。训练是一次性投入，推理是持续性支出：一次对话请求可能只生成几百个 token，但背后需要反复读取模型权重、维护 KV Cache、执行注意力计算。随着上下文窗口从 2K 扩展到 32K 甚至 128K，KV Cache 的增长速度远快于权重，显存成为最稀缺的资源。与此同时，在线服务的请求到达具有明显的突发性，长度分布高度偏斜：少量长请求会显著拖慢整批短请求。对服务提供方而言，真正决定成本的不是单卡峰值算力，而是“在满足延迟 SLO 的前提下，一张卡能同时服务多少请求”。

**（2）技术现状。** 围绕上述问题，工业界形成了若干相对成熟的技术路线。其一是 KV Cache 的分页化管理：把 KV 按固定大小的块切分，用页表维护逻辑位置到物理块的映射，从而消除“按最大长度连续预占”造成的浪费。其二是连续批处理：请求不再按批次等齐，完成的请求立即离队，新请求随时插入空槽，使 GPU 在时间维度上保持饱和。其三是前缀共享与写时复制：相同系统提示词或相同对话前缀的 KV 块被多个请求共享，只有分叉处才复制。其四是分层加载与预取：当模型大于单卡显存时，权重按层从主机内存或 NVMe 加载，通过双缓冲把 DMA 与计算重叠。其五是虚拟化与超卖：通过客户物理页到宿主物理页的映射，让多个租户的逻辑显存之和超过物理显存，并以气球（balloon）机制回收冷页。其六是多租户公平调度：在共享 GPU 上按份额分配时间片，避免某个租户的突发流量长期压制其他租户。

**（3）国外现状。** 学术界与开源社区起步较早。vLLM 提出 PagedAttention，把操作系统的虚拟内存与分页思想引入 KV Cache 管理，并配合连续批处理，在相同硬件上把吞吐提升数倍；Orca 较早系统化了连续批处理中的迭代级调度；TensorRT-LLM 在工程实现上进一步引入 in-flight batching 与多种量化路径；SGLang 的 RadixAttention 用基数树管理前缀复用，把多轮对话与少样本场景的缓存命中率进一步提升；DeepSpeed-FastGen 用动态 SplitFuse 把长请求切块混批，缓解长短请求相互拖累；DistServe 与 Sarathi-Serve 则从“预填充与解码分离”“分块预填充”的角度重新划分资源。这些工作共同说明：推理系统的性能差距，很大程度上来自调度与内存管理，而不是模型结构本身。

**（4）国内现状。** 国内在工程落地与生态适配上进展很快。LMDeploy 针对国产与国际 GPU 提供了较完整的推理服务能力；华为 MindIE 面向昇腾生态做了图优化与多卡并行；互联网厂商在大规模集群上普遍自研了带 SLO 保障的调度层，并在 KV 缓存分层卸载、前缀缓存复用等方向积累了大量工程经验。开源层面，国内团队对 vLLM、SGLang 的贡献也在增加。总体来看，单点机制上国内外差距在缩小，差距更多体现在超大规模集群的稳定性、异构硬件的适配深度以及面向具体业务的 SLO 调度策略上。

**（5）教学与原型的空白。** 尽管工业实现已经相当成熟，但作为操作系统课程的教学素材，仍缺少“可解释、可复现、可干预”的定量材料。直接阅读 vLLM 源码门槛高，且其默认实现把多种优化耦合在一起，很难单独观察某一项机制的作用；直接在真实 GPU 上做对照又受硬件与成本限制。本项目因此选择“仿真内核 + 真实 GPU 背书”的路线：在纯 Python 的离散事件仿真中把分页、COW、批处理、公平调度、预取、超卖逐项拆开做 A/B 对照，再用一次真实模型实验验证方向一致性。这样既能回答“每项机制贡献多少”，又不会把结论建立在某台特定机器上。

**（6）本场景的约束与目标。** 场景采用单卡、双租户、固定模型规模的设定，负载由泊松过程合成，prompt 长度 2048–4096、生成长度 256–512，突发系数 6。核心约束包括：显存池 1024 块、每块 16 token；权重分层加载带宽 3.5 GB/s（NVMe）、16 GB/s（主机到 GPU）、800 GB/s（HBM）；预取窗口 2 层；MPS 时间片 10 ms；饥饿判定为等待时间超过最短作业时间的 10 倍。目标是在该约束下同时满足：OOM 率为 0、TTFT P50 不超过 1 秒、跨租户 P99 方差显著下降、越界拦截率 100%。

**（8）国内外差距的具体体现。** 第一，单点机制上的差距在缩小。分页 KV、连续批、前缀复用、分块预填充这些机制，国内外系统都有对应实现，论文与开源代码的传播速度也很快，单纯“有没有某个优化”已经很难构成差距。第二，系统集成与超大规模稳定性上的差距仍然明显。万卡级集群的故障注入、慢节点检测、拓扑感知调度、跨租户 SLO 保障，需要在真实生产流量中长期打磨，难以通过阅读代码获得。第三，硬件生态适配深度不同。CUDA 生态的工具链、算子库与调试手段更成熟，国产加速卡在算子覆盖、图编译与性能分析工具上仍在追赶，这直接影响同一机制在不同硬件上的落地成本。对本项目而言，这三条差距意味着：机制层面的结论可以较有信心地迁移，但具体时延数字必须绑定具体硬件，不能把仿真值当作某张卡的真实性能。

**（9）教学与原型层面的空白。** 操作系统课程的实验通常围绕 xv6、Nachos 或 Linux 内核模块展开，负载是 shell 命令与文件读写，很少涉及“按序列增长的内存对象”“批处理的空泡”“权重分层加载”这类 AI 负载特征；而大模型相关的课程又往往停留在调用 API、微调模型或使用推理框架，学生看不到调度器与内存管理器内部。结果是两边各缺一块：OS 课程缺少现代负载，AI 课程缺少系统视角。本项目选择用纯 Python 仿真补上这块空白，原因有三：一是仿真可以把“时间”变成可编程对象，任意放慢、放大、重放；二是仿真允许故意制造 OOM、越界、饥饿等真实环境难以稳定复现的边界；三是仿真代码量可控，学生可以在一个学期内读完并改动核心逻辑。真实 GPU 只承担方向背书，不承担教学主链路，这样即使没有显卡也能完成 90% 以上的工作。

**（10）场景与负载选择的依据。** 选择“双租户 + 混合敏感度”而不是单租户，是因为单租户下公平性、配额、隔离这些机制根本不会被触发，实验会退化成纯吞吐测试。选择 W1（短对话，prompt 32–128、gen 32–128、到达率 40/s）与 W2（长上下文，prompt 2048–4096、gen 256–512、到达率 6/s）两套负载，是因为它们分别对应“批处理效率”与“显存容量”两类瓶颈：W1 下静态批的空泡最明显，W2 下连续预占的 OOM 最明显。W3 在 W1 基础上加入每租户 6 次连续到达的突发，用来制造租户间的争抢；W4 固定 48 token 前缀、4 路分支，用来单独观察 COW。泊松到达而非固定间隔，是为了让队列长度自然波动，避免“每拍刚好一条请求”这种过于理想的时序。所有负载只使用 `random.Random(seed)`，因此同一 seed 下的到达序列、长度分布与分叉结构完全一致，A/B 两组看到的输入逐条相同——这是所有对照结论成立的前提。

### 3.2 系统实现

系统实现遵循第 2 章的分层结构，内核与评测分离、仿真与真机分离。内核不依赖任何第三方库，评测服务只通过实验编排层调用内核，真机适配器独立于二者，结果分别落在 `results/` 与 `gpu_results/` 两个目录，禁止混表。下面按模块说明详细设计。

#### 3.2.1 模块详细设计

##### 3.2.1.1 功能概述

本模块组由五个模块构成：KV 内存管理、批处理调度、分层预取、GPU 虚拟化与配额、实验编排与评测服务。KV 内存管理负责把序列的逻辑 KV 位置映射到物理块，并处理共享、换出与回收；批处理调度负责决定每一拍哪些请求进入 GPU、以什么顺序进入；分层预取负责在计算当前层的同时把后续层搬到显存，并统计停顿；GPU 虚拟化与配额负责多租户地址空间、超卖与硬上限；实验编排与评测服务负责把上述机制组织成 13 组可对照的实验，并把结果结构化输出给界面与报告。

##### 3.2.1.3 处理流程

**KV 内存管理。** 第一步，序列每追加一个 token，按 `ceil((prompt+gen)/16)` 计算所需块数；第二步，若当前块表不足，从空闲栈取块并写入页表；第三步，空闲栈为空时调用 `steal_for_eviction(now)`，仅允许驱逐引用计数为 1 的块，共享块必须先分裂；第四步，仍不足则抛出 `AllocError`，由调度器将该请求标记为失败；第五步，序列完成或分叉结束时递减引用计数，归零才归还空闲栈；第六步，每拍采样碎片率与利用率，写入时间序列。

**批处理调度。** 以持续批为例：每拍开始回收已完成槽位，从就绪队列按策略补入新请求；然后计算本拍代价（prefill 按 token 数、decode 按批大小），推进所有处于 RUNNING 的序列；若某序列超过时间片仍未完成，抢占式调度将其置为 PREEMPTED 并保存进度；若某租户的等待时间超过饥饿阈值，公平调度提升其权重。静态批则等待整批完成后统一换批，用于对照。

**分层预取。** 每拍先确定当前需要计算的层；若该层未驻留，计算从 NVMe 或主机内存搬运所需时间并登记 DMA 完成事件；双缓冲模式下，在计算第 i 层的同时发起第 i+1 层的搬运；层缓存命中时直接跳过搬运；本拍 stall 定义为 `max(0, 数据就绪时刻 - 当前时刻 - 本拍计算时间)`，即只统计“等待数据”的时间，DMA 忙碌本身不计入 GPU 有效算力。

**GPU 虚拟化与配额。** 租户创建时为每个客户页建立映射，物理页不足即构成超卖；访存时先检查 vpn 是否越界、映射是否存在，越界抛 `IsolationError` 并计入拦截；缺页时触发换入，若物理页耗尽则按 LRU 选择冷页换出，脏页需额外计入写回延迟；balloon 回收按租户压力选择未被 pin 的冷页；配额层在请求准入时按块粒度预留，超出硬上限直接拒绝。

##### 3.2.1.4 数据结构

KV 内存模块的核心结构如下，块池用列表维护，空闲块用栈维护，页表用字典把序列映射到块列表：

```python
@dataclass
class Block:
    bid: int              # 物理块号
    ref_count: int = 0    # 0=空闲, 1=独占, >1=共享(COW)
    owner: int | None = None
    last_used: float = 0.0

class BlockAllocator:
    blocks: list[Block]
    free_stack: list[int]
    def allocate(self, n: int, now: float, seq: int) -> list[int]
    def free(self, bids: list[int]) -> None
    def fork(self, src: int, dst: int) -> None
    def steal_for_eviction(self, now: float) -> list[int]
```

调度模块用槽位（Slot）表示本拍占用，用租户账本记录累计服务时间，保证 FAIR 与 MPS 份额来自同一配置源：

```python
@dataclass
class Slot:
    req_id: int
    tenant: str
    state: str            # WAITING/RUNNING/PREEMPTED/FINISHED
    kv_blocks: list[int]

@dataclass
class TenantLedger:
    share: float          # 与 MPS 共用同一份额配置
    served: float = 0.0
    wait_since: float = 0.0
```

预取模块用层状态表记录每层是否驻留、最后一次访问时间，用 span 列表记录 compute 与 DMA 的时间区间，供 overlap 图与 stall 统计使用：

```python
@dataclass
class LayerState:
    layer: int
```

##### 3.2.1.5 模块协作与端到端时序

四个子系统不是并列的四个 demo，而是被同一条请求串起来的流水线。以一条 W1 请求为例，其完整生命周期如下：

1. **到达与准入（t=0）。** 负载生成器按泊松过程在 `t` 时刻把请求提交给调度器；调度器先向配额管理器申请该请求预计占用的块数，若超过租户硬上限则抛 `QuotaOOM`，请求直接记为失败，不进入等待队列。
2. **排队与选批（t=0）。** 请求进入 WAITING 队列。调度器在下一个 `DecodeTick` 中按策略排序：FCFS 按到达顺序，SJF 按剩余长度，FAIR 按“已准入次数/份额”的亏空排序。选中的请求被标记为 RUNNING。
3. **页表建立（t=0）。** 调度器调用 `PageTable.new_sequence`，分配器按块申请物理块，并通过 `GPUVMM.pin` 把块映射到宿主物理页。若 `pin` 因越界失败，分配器回滚已拿到的块并抛 `AllocError`，调度器把该请求标记为失败。
4. **预填充（t=0）。** 本拍代价为 `alpha_prefill × prompt_tokens`，加上预取产生的 stall 与 MPS 上下文切换开销；若该请求是长上下文，块数会随 token 逐拍增长。
5. **解码循环（t>0）。** 每拍回收已完成槽位、补入新请求、推进所有 RUNNING 序列各一个 token，并调用 `append_token` 追加逻辑页。跨块时自动扩块；空闲栈耗尽时先换出独占块，共享块必须先 COW 分裂。
6. **抢占与公平（任意拍）。** 若某序列超过时间片仍未完成，抢占式策略把它置为 PREEMPTED 并保存进度；若某租户的等待时间超过 `10 × 平均单拍时长`，FAIR 在下一个窗口提升其权重。
7. **完成与释放（t=T）。** 序列生成长度耗尽后置为 FINISHED，引用计数递减，归零的块归还空闲栈并 `release` 宿主页；脏页换出会额外计入写回延迟。
8. **归集（运行结束）。** 实验编排层从指标总线读取吞吐、TTFT、P99、KV 利用率、碎片率、换出次数、stall 与拦截率，按 `_pack` 组装为统一结构。

表3-7　请求状态迁移

| 当前状态 | 触发事件 | 下一状态 | 系统动作 |
| --- | --- | --- | --- |
| 未到达 | 泊松到达 | WAITING | 配额准入；超限则直接 FAILED |
| WAITING | 被选入本拍批 | RUNNING | 建页表、pin 物理页、分配 KV 块 |
| RUNNING | 本拍推进一个 token | RUNNING | 追加逻辑页；跨块时扩块 |
| RUNNING | 超过时间片 | PREEMPTED | 保存进度、释放时间片、记录上下文切换 |
| PREEMPTED | 重新被选中 | RUNNING | 恢复进度；必要时换入被换出的块 |
| RUNNING | 生成长度耗尽 | FINISHED | 释放 KV 块与物理页、统计延迟 |
| WAITING/RUNNING | `AllocError` / `QuotaOOM` | FAILED | 回滚分配、计入 OOM、不计入完成数 |

这套时序的关键在于“时间只从事件堆来”。第 4 步的预填充代价、第 5 步的单拍代价、第 7 步的写回延迟，全部以 `schedule(delay, fn)` 表达，没有任何一处依赖真实时钟。因此只要 seed 与配置相同，上面 8 步的每一步发生时刻都完全一致，任何一拍的甘特图都可以被逐帧复现。

#### 3.2.2 接口

系统接口分为两层：内核层的冻结契约与对外服务层的 REST 接口。内核层不依赖任何网络框架，只以普通 Python 方法与协程暴露能力；服务层只做参数校验、结果落库与序列化，不包含任何仿真逻辑。这样既保证了内核可以被单元测试直接驱动，也保证了服务层替换（例如从本地 FastAPI 换成云端服务）时不会影响实验语义。

#### 3.2.3 关键代码解释

本节选取六段最能体现设计取舍的代码，说明“为什么这样写”，而不是逐行翻译。

**（1）离散事件钟。** 全部时间推进只经过一个 `heapq` 事件堆，禁止 `time.sleep` 与线程：

```python
def schedule(self, delay, fn, priority=0, kind=""):
    if delay < 0:
        raise ValueError("delay must be >= 0")
    heapq.heappush(self._heap, _Event(self._now + delay, priority, self._seq, fn, kind))
    self._seq += 1

def step(self) -> bool:
    if not self._heap:
        return False
    ev = heapq.heappop(self._heap)
    self._now = ev.time
    ev.last_kind = ev.kind
    ev.fn()
    return True
```

这里的关键是 `_Event` 的排序键为 `(time, priority, seq)`：同一时刻的多个事件按优先级、再按入堆顺序出堆，因此“同一拍谁先执行”是确定的。若用真实线程与 `sleep`，调度顺序由操作系统决定，同一 seed 两次运行会得到不同结果，A/B 对照就失去意义。`seq` 单调递增还解决了浮点时间相等时 `heapq` 比较回调函数的报错问题。

**（2）分页分配与换出回滚。** `allocate` 在失败路径上必须把已拿到的块全部归还，否则一次失败会永久泄漏块，把 OOM 率算低：

```python
for _ in range(n):
    if not self._free:
        if not self.allow_eviction:
            for bid in out:
                self.free([bid])
            raise AllocError("contiguous pool exhausted (eviction disabled)")
        stolen = self.steal_for_eviction(self.now, exclude=set(out))
        if stolen is None:
            for bid in out:
                self.free([bid])
            raise AllocError("no free KV blocks after eviction")
    bid = self._free.pop()
    ...
    out.append(bid)
```

`exclude=set(out)` 是第二个关键点：换出候选不能是本次刚分配出去的块，否则会出现“自己换出自己”的死循环。牺牲块的筛选条件为 `ref_count == 1`，即共享块绝不换出——共享块被换出会让多个序列同时失效，正确做法是先 COW 分裂，再让其中一份成为独占块后才有资格被驱逐。

**（3）持续批的单拍主循环。** 每一拍都先回收、再补位、再推进，使 GPU 不因等待整批对齐而空转：

```python
def _decode_tick(self) -> None:
    self._reap_finished()
    batch = self._pick_batch()
    if not batch:
        if self.waiting or self.running:
            self.sim.schedule(self.idle_tick, self._decode_tick, kind="DecodeTick")
        else:
            self._scheduled = False
        return
    admitted, mps_extra = self._confirm_slice(batch)
    ...
    cost = self._iteration_cost(work) + stall + mps_extra
    for req in admitted:
        ...
        req.step(self.sim.now)
        self.page_table.append_token(req.seq_id)
    self.busy_time += cost
    self.sim.schedule(max(cost, self.idle_tick), self._decode_tick, kind=nxt)
```

与静态批的区别集中在 `_pick_batch`：静态批在整批完成前不补位，持续批每拍都把空槽填满，因此 `busy_time` 占墙钟时间的比例更高。`max(cost, self.idle_tick)` 保证即使代价趋近于 0 也不会出现同一时刻无限循环。饥饿判定使用 `10 × 平均单拍时长` 作为阈值，而不是写死的秒数，因为仿真时间与真实时间没有可比性，只有相对倍率才有物理含义。

**（4）无 sleep 的异步预取契约。** `decode_step` 是协程，但 await 的对象是一个“已经算出完成时刻”的句柄：

```python
async def decode_step(self, layer, sim=None) -> float:
    n = len(self.layers)
    if n == 0:
        return 0.0
    sim = sim if sim is not None else DiscreteEventSim()
    idx = layer % n
    wait = self._advance(sim, idx)
    await _DmaHandle(self._issued.get(idx, sim.now))
    return wait
```

`_advance` 在 await 之前就已经把 DMA 完成事件 `schedule` 进了事件堆，并把完成时刻记在 `_issued`。`_DmaHandle.__await__` 只是把这个时间戳解包返回，并不真正挂起协程。这样既满足技术方案 §5.3 的协程签名要求，又保证结果只依赖事件堆而不依赖 asyncio 的任务调度顺序。测试 `test_prefetch_decode_step_contract` 同时断定了三点：是协程函数、同一配置下 stall 与 `tick()` 路径完全相等、await 不产生真实挂起。

**（5）越界拦截与加权份额。** 访存路径把“不存在的 vpn”和“物理页耗尽”都收敛为拒绝，而不是悄悄返回一个错误页：

```python
def access(self, tenant, vpn, write, now) -> int:
    table = self.tables.get(tenant)
    if table is None or vpn not in table:
        self.violations_attempt += 1
        raise IsolationError(f"{tenant} vpn={vpn}")
    page = table[vpn]
    if not page.resident:
        self.page_faults += 1
        if not self.free_ppn:
            self._evict(now)
        if not self.free_ppn:
            raise IsolationError("no physical pages")
        page.ppn = self.free_ppn.pop()
        page.resident = True
    page.last_access = now
    if write:
        page.dirty = True
    return int(page.ppn)
```

拦截计数与实际违规计数分开统计：`violations_attempt` 记录“试图越界”的次数，`isolation_violation_rate` 记录“越界真正读写成功”的比例。前者用来证明压力测试确实打到了边界，后者必须恒为 0。MPS 侧则用加权亏空（`accumulated / share`）选举窗口占有者，保证 1:1 时两租户各得一半、3:1 时严格按 3:1 分配，且不在每个时间片强行切换，从而把上下文切换开销从 0.0494 降到 0.0250。

**（6）实验编排与 A/B 构造。** 13 组实验共用同一个服务函数，基线与优化只是同一函数的不同关键字参数，从代码结构上杜绝“两套仿真各算各的”：

```python
def run_serving(reqs, cfg=None, *, mode="continuous", strategy="fcfs",
                kv_mode="paged", num_blocks=None, phys_pages=None,
                share_alpha=None, share_beta=None, mem_cap=None, tenants=None):
    ...
    alloc = BlockAllocator(
        num_blocks=num_blocks, block_size=block_size, vmm=vmm,
        allow_eviction=(kv_mode == "paged"),
    )
```

`kv_mode` 决定分配器是否允许换出，这是 E1 的唯一开关；`mode` 决定静态批还是持续批；`strategy` 决定 FCFS/SJF/抢占/FAIR；`share_alpha/beta` 决定租户份额；`phys_pages` 决定超卖比。E1 的调用因此可以写成“同一批 `reqs`，一次 `kv_mode="contiguous"`、一次 `kv_mode="paged"`”，除这一个参数外没有任何差异。若把基线写成另一段独立代码，即便结论方向正确，也无法排除实现差异带来的干扰。

结果组装同样只有一条路径，`_pack` 统一产出报告与前端需要的全部字段：

```python
return {
    "id": exp_id,
    "title": title,
    "baseline": _public(base),
    "optimized": _public(opt),
    "extra": extra or {},
    "charts": {...},
    "gantt": {"baseline": base.get("gantt", []), "optimized": opt.get("gantt", [])},
```

`_public` 只保留可序列化的指标，`_kpis` 统一计算基线与优化的差值，`config_digest` 把配置变成可核对的指纹。这样一来，报告、图表、前端读的是同一份结构，任何一处数字对不上都能立刻定位到是数据问题还是展示问题。

#### 3.2.4 碰到的问题及解决方案

表3-12　主要问题与解决方案

| 序号 | 问题现象 | 根因分析 | 解决方案 | 验证方式 |
| --- | --- | --- | --- | --- |
| 1 | 早期版本用线程与 sleep 模拟并发，同一 seed 两次运行结果不同 | 线程调度顺序与真实时间不可控，浮点累加顺序漂移 | 改为单线程 `heapq` 事件堆，所有延迟以 `schedule` 表达；`decode_step` 的 await 只解包已定时间戳 | 连跑两次 E1/E4/E7/E9，JSON 逐位相同 |

其中第 5 条是本项目最重要的“负结果”。它说明预设想当然的结论必须被数据检验：分页不是万能的碎片解药，它的价值在于“按最大长度预占”变成“按需增长”，从而消除 OOM 并提高并发；代价是页表开销、换出开销与块内碎片。报告选择保留这一负结果，而不是换一个对自己有利的指标，这也是本项目的可信度来源。

**复盘一：可比性是设计出来的，不是声明出来的。** 最初的 E1 之所以被质疑，是因为“分页”一组同时打开了换出、缩小了预占粒度、还改了并发上限，三个变量一起变，结论自然不可信。修正的做法不是去解释，而是把变量收敛到一个开关，并在结果里写入配置摘要。这件事之后，我们给每个实验都加了一条自检：如果两组配置的差异不止一个字段，就拒绝出图。这条自检后来还拦下了 E5 的一次误配——抢占组不小心继承了 SJF 的排序，导致 TTFT 的改善被高估。

**复盘二：指标口径必须写进代码，而不是写在文档里。** E7 的 `io_stall_ratio` 一度大于 1，原因是 stall 把 DMA 忙碌时间也算进去了，而 compute 又叠加了一次。文档里写“stall 是等待数据的时间”没有用，必须让代码只有一个定义、两条路径共用同一个 `_advance`。同理，FAIR 与 MPS 的份额如果各有一本账，文档写“按份额”也救不了 3:1 跑成 1:1。我们最终的约定是：任何指标只允许有一个计算入口，测试断言两条路径数值相等，文档只是对代码的解释。

**复盘三：平台差异要标注，不要抹平。** 真机 G1 最初在 Windows 上扫不到 OOM，因为 WDDM 会把超出的显存回溢到主机内存，表现为“变慢”而不是“报错”。如果直接把这种结果写成“未出现 OOM”，就会得出与 Linux 相反的结论。解决办法是显式区分平台：Windows 上用物理显存的 0.98 倍作为阈值，Linux/Colab 上走真实 CUDA OOM 分支；同时在报告里注明阈值来源。类似地，消费级显卡的 decode 斜率接近 0，与数据中心的线性模型形态不同，我们选择如实记录差异，而不是把仿真参数调成能拟合真机的值。

#### 3.2.5 评测台与真机适配

评测台不是报告的点缀，而是“实验可被复现、可被质疑”的入口。它的设计原则只有一条：前端不计算任何指标，只做三件事——发起运行、按 `run_id` 取结果、把结果渲染成可对照的视图。所有数字都来自后端返回的 JSON，前端不缓存、不推导、不拼接，从结构上避免“界面显示与实验结果不一致”。

**（1）状态管理。** 页面状态由五个字段构成：当前实验 `selected`、当前种子 `seed`、运行中标志 `running`、当前结果对象 `result`、运行令牌 `runToken`。点击“运行”时先自增令牌，异步返回后只有在令牌仍相等时才写入结果；这样即使后端响应乱序，旧结果也不会覆盖新结果。切换实验时立即清空 `result` 并中止未完成的请求回填，避免“切到 E4 却看到 E1 的图”。页面地址同步为 `?exp=E4&seed=42&run=12`，刷新或分享链接即可回到同一次运行，这对答辩现场复现某一张图非常关键。

**（2）渲染。** 图表全部用手写 SVG，不引入图表库。原因是本项目的图有两类特殊需求：甘特图要左右并排展示基线与优化的逐拍轨迹，并在同一行标注租户、请求号与 DMA 停顿；折线/柱状图要在悬浮时同时显示两组数值。通用图表库要么难以定制这种并排结构，要么会引入较大的打包体积。手写 SVG 的代价是需要自己处理坐标换算、刻度与提示框定位，但换来的是完全可控的视觉表达与零运行时依赖。悬浮提示按“最近点”匹配，十字线跟随鼠标，提示框在右侧空间不足时自动翻转到左侧，避免遮挡曲线。

**（3）历史与导出。** 每次运行落库后生成一条历史记录，包含运行号、实验、种子、结论与时间。历史面板支持按实验筛选、按结论高亮、收藏常用运行；点击某条记录即按 `run_id` 回放，而不是重新运行。导出提供两种格式：JSON 用于核对原始指标，PNG 用于直接插入报告。PNG 由 SVG 序列化后绘制到画布导出，不依赖后端截图服务。快捷键 `R` 运行当前实验，`1`–`4` 切换到四个必做实验，另有“演示四组”按钮按 E1→E4→E7→E9 顺序批量运行，用于答辩时快速铺满证据链。

**（4）真机适配。** 真机部分独立在 `adapters/gpu_g1.py`，不导入内核的任何调度代码。脚本做三件事：加载本地 Qwen2.5-0.5B（FP16），在固定 prompt 与固定生成长度下分别用 `StaticCache` 与 `DynamicCache` 逐档增加并发，直到装不下为止；记录每档的峰值显存、吞吐与首 token 延迟；把结果写入 `gpu_results/g1.json`，并给出 `CONSISTENT_WITH_SIM_E1` 之类的判定。装得下的判定在 Windows 上用物理显存的 0.98 倍作为阈值，在 Linux/Colab 上则捕获真实 CUDA OOM。子进程注入 `PYTHONIOENCODING=utf-8`，日志实时回传前端面板，因此面板上能看到“加载模型—预热—逐档加压—判定”的完整过程。

**（5）校准与隔离。** 同一适配器还负责代价校准：固定生成长度、扫描批大小，用最小二乘拟合“每批固定开销 + 每 token 边际开销”，结果写入 `gpu_results/calibration.json`。校准值只用于讨论仿真参数的量级是否合理，不回写 `defaults.yaml`，也不参与任何实验结论。这条隔离是刻意的：如果让真机数据反过来决定仿真参数，再用仿真去“预测”真机，就成了循环论证。评测台在界面上也做了区分：仿真实验的结果页与 GPU 背书面板分属不同入口，数据目录不同，避免观众误以为 13 组实验都跑在真机上。

**（3）必做四组的深入分析。**

E1 是本项目的起点实验。连续预占按最大长度一次性占满，11 条请求中有 5 条因显存不足失败，OOM 率 45.45%；分页按需增长，OOM 降为 0，峰值并发从 2 升到 6，活跃序列从 1 升到 6。代价是换出 812 次与页表开销，吞吐从 2.738 降到 2.165。这里必须强调：分页解决的是“能不能跑”，不是“跑得多快”；在长上下文场景（E11）中这一结论更明显，OOM 从 42.86% 降到 0，并发从 2 升到 4，而吞吐同样下降 11.4%。

E4 说明持续批的收益来自消除“等待最长序列”的空泡。静态批必须等整批全部完成才能换批，短请求完成后槽位空转；持续批每拍补位，GPU 忙闲比从 0.9518 升到 0.9888，吞吐提升 17.1%，首 token 延迟下降 35.4%。值得注意的是饥饿占比两侧都是 0.75，说明持续批本身不解决公平问题——这正是 E6 存在的理由。

E6 把 FCFS 换成按份额选举的 FAIR。跨租户 P99 方差从 0.0271 降到 0.0040，降幅 85.2%，吞吐只损失 0.9%，且在 5 个 seed 下均成立。这一结果回答了“公平是否必然牺牲吞吐”的问题：在本负载下，公平几乎不花钱，因为被压制的租户原本就在制造拥塞。

E7 的收益来自把 DMA 与计算重叠。串行方案的 I/O 停顿占比高达 93.46%，GPU 大部分时间在等权重；双缓冲加层缓存后降到 81.69%，有效算力从 6.54% 升到 18.31%，提升 180%。这里的绝对数值仍然偏低，原因是仿真中“每层权重”相对于带宽过大；但相对改善与 overlap 图（compute 与 DMA 两层时序）给出了清晰的因果解释。

E9 验证的是“超卖不等于越界”。物理 16 页、逻辑 40 页时超卖比 2.5，全部越界访问被拦截，违规率为 0，balloon 回收 4 页；延迟随超卖比从 1.0 到 5.0 单调上升，形成可解释的 Pareto 前沿。这条结论的意义在于：超卖的安全性不取决于运气，而取决于地址翻译与拦截是否在每一次访存上执行。

**（4）真实 GPU 方向背书。** 仿真结论必须面对“是不是自说自话”的质疑，因此用本地 RTX 5060 与 Qwen2.5-0.5B（FP16）做了 G1 对照：静态侧用 `StaticCache` 按 `max_tokens=2048` 预占整条 KV，动态侧用 `DynamicCache` 按需增长，每条序列实际只跑 32+32 token。结果为静态预占最大可承载 192 条并发（峰值 7.715 GB），按需增长可承载 640 条（峰值 7.749 GB），提升 ≥3.33 倍，越界点分别为 N=256 与 N=640 处的真实 OOM，verdict 为 `CONSISTENT_WITH_SIM_E1`。这不能替代仿真，但足以证明“预占→OOM、按需→承载更高”的方向在真实引擎上同样成立。

真机同时暴露了一个必须如实记录的差异：代价参数校准显示 prefill 边际速率为 0.122 ms/token，约为仿真冻结值 0.02 ms/token 的 6 倍；decode 拟合斜率接近 0（29.5 ms + 0.20 ms/批，R²=0.39），呈现桌面卡 eager 模式下的 kernel 发射地板。这说明仿真刻画的是数据中心级线性代价模型，而不是某张消费级显卡的具体时延。校准结果只作为灵敏度附录，不回写冻结配置，避免“用真机数据反向拟合仿真”这种循环论证。

**（5）可复现性与回归。** 内核中不存在 `time.sleep` 与 `asyncio.sleep`，负载只用 `random.Random(seed)`，预取完成时刻进入事件堆，`decode_step` 的 await 不产生挂起。同一 seed 连续两次运行，E1/E4/E7/E9 的 JSON 逐位相同，由 `test_golden_w1_e4_repeatable` 与 `test_e1_e7_e9_have_digest_and_two_columns` 固化。回归建议是：改动调度、分配器或预取后至少执行 `pytest -q` 与 `run_ab.py`，并重点复核三处——E1 的 `oom_ratio` 是否仍为 0、E7 的 `io_stall_ratio` 是否仍下降、E6 在 5 个 seed 下方差是否仍下降。

**（6）前端与演示链路验证。** 前端构建通过，浏览器实测覆盖了深链恢复（`?exp=E7&seed=42&run=12`）、切换实验清空旧结果、运行期间禁止切换实验、四个必做实验一键批量运行、甘特图基线/优化并排、折线/柱状图悬浮取值、历史记录筛选与收藏、结果 JSON/PNG 导出。验证过程中发现并修复了一处模板残留引用（`ganttRows` 未定义导致渲染报错），修复后控制台零错误。这一层测试虽然不产出学术结论，但它保证了答辩现场不会因界面问题打断论证。

**（7）其余实验的补充分析。** E2 固定 48 token 前缀、4 路分叉，独立拷贝需要 12 个物理块，COW 只需 6 块，且分叉越多节省越明显；这说明前缀共享的收益与分支数近似线性，但前提是写时分裂必须正确，否则共享块被就地修改会污染其他分支。E3 对比大池与“小池 + LRU”：大池换出 0 次、利用率 0.503，小池换出 744 次、利用率 0.999，两者都没有 OOM。这组实验想说明的是“容量与换出可以互换”，但换出不是免费的——每次换出都意味着后续可能的换入延迟，所以它适合作为容量不足时的兜底，而不是默认策略。

E5 用抢占换尾部延迟：TTFT P50 从 0.674 降到 0.120，饥饿占比从 0.75 降到 0.625，代价是吞吐下降 2.3%。这组数字很小，但方向很关键：抢占不是“让系统更快”，而是“让等待更公平”，它把长请求的完成时间推后，换取短请求不被堵在队头。E8 的配额硬上限则展示了“拒绝”的价值：开启上限后 OOM 率 0.294、并发从 5 降到 4，看似变差，但拒绝是可预期的、局部的，而未设上限时一个租户的突发会把整卡拖入 OOM，影响所有租户。

E10 验证 MPS 份额：1:1 时 α、β 各得 0.40，3:1 时 α 得 0.60、β 得 0.20，Jain 公平指数为 1.0，切换开销从 0.0494 降到 0.0250。E11 把上下文拉到 8K 以上，连续预占 OOM 率 42.86%，分页为 0，并发 2→4，吞吐代价 11.4%——这是 E1 结论在长上下文下的复现，也说明分页的必要性随上下文长度单调上升。E12 用预取把单卡可承载的模型规模从 4 GB 拉到 16 GB，提升 300%，因为它把“整模型常驻”变成了“按层换入”；代价是每层都要付出 DMA 时间，收益取决于计算/带宽比。E13 把租户从 2 个增到 8 个，Jain 从 0.9966 降到 0.8957，吞吐基本持平——多租户的代价主要体现在公平性而非总吞吐，这一点与直觉相反，值得在答辩中主动说明。

**（8）压力与边界测试。** 除常规对照外，还专门测试了六类边界。第一，超卖比扫描：从 1.0 到 5.0 逐档提高逻辑页/物理页比例，延迟单调上升、换出次数单调增加，但没有出现违规访问，说明超卖的安全性由拦截机制保证，而不是由比例本身保证。第二，批大小为 1 与 8 的极端：批大小为 1 时退化为逐条执行，吞吐最低但延迟最稳；批大小为 8 时吞吐最高，但尾延迟抬升，这一对照解释了为什么生产系统需要动态批而不是固定批。第三，空队列：所有请求完成后调度器不再注册新的 `DecodeTick`，仿真时钟自然停止，不会出现“空转导致时间无限推进”的问题。第四，长上下文溢出：prompt 超过单序列最大块数时，分配器在扩容失败处回滚并标记失败，不会留下半建成的页表。第五，配额边界：申请恰好等于上限时允许，超过 1 块即拒绝，验证了“等于”与“大于”的判定没有差一错误。第六，8 租户并发：在 8 个租户同时突发时，拦截率与违规率仍分别为 1.0 与 0，说明隔离不依赖租户数量。

## 4. 总结

### 4.1 项目创新或特色

**（1）用操作系统课程的主线重构了推理系统。** 项目没有停在“调一个推理框架的参数”，而是把分页、写时复制、LRU 换出、进程调度、时间片、公平份额、虚拟内存、气球回收这一整套操作系统概念，逐一映射到 KV Cache、批处理、MPS 与 GPU 虚拟化上，并用同一套请求状态机把它们串成一条完整路径。这种映射不是比喻，而是可执行的结构对应：`BlockAllocator` 就是物理页分配器，`PageTable` 就是页表，`GPUVMM` 就是带越界检查的 MMU。

**（2）13 组冻结配置的 A/B 实验，把“机制贡献”拆开量化。** 工业实现往往把分页、连续批、前缀共享、超卖耦合在一个默认配置里，很难回答“哪一项贡献了多少”。本项目以固定 seed、固定块大小、固定带宽、固定时间片为前提，对每一项机制单独做对照，并给出基线与优化后的完整双列指标。这使得结论可被逐条检验，也使负结果（如 E1 碎片率上升）无法被掩盖。

**（3）可复现性被当作一等公民。** 纯标准库实现的离散事件钟、无 `sleep`、无线程依赖、黄金 trace 逐位比对、配置摘要入库，这些工程约束换来的是“任何人任何机器跑同一命令得到同一结果”。对于课程项目而言，这比多跑几个漂亮数字更重要，因为它让结论可被质疑、可被重跑、可被推翻。

**（4）仿真与真机双轨，且严格隔离。** 仿真负责“可解释、可干预、可穷举”，真机负责“方向背书”。两者结果分别落在 `results/` 与 `gpu_results/`，不混表、不互相拟合；真机校准只作为灵敏度附录，不回写冻结配置。这种隔离避免了“用真实数据调参再声称预测准确”的常见陷阱。

**（5）评测台把实验变成了可演示的产品。** 前端不是图表的堆砌，而是以“实验—运行—对照—回放”为主线的评测台：深链可复现某次运行、切换实验自动清空旧结果、运行期间锁定导航、首次进入提供四组必做实验的一键批量运行、甘特图基线/优化并排、图表悬浮取值、历史记录可筛选收藏、结果可导出 JSON 与 PNG。

**（6）主动记录未达预期的指标。** 技术方案曾预期分页会“显著降低碎片”，实测碎片率反而从 0.160 升到 0.469。项目没有换指标、没有删结论，而是在量化报告、测试报告、答辩脚本三处统一说明原因（块内碎片与空闲链分散），并把收益重新锚定在 OOM 消除与并发提升上。这种处理方式本身就是工程素养的一部分。

### 4.2 心得体会

这次实习最开始，我们对“操作系统”和“大模型推理”的关系理解得比较表面：觉得一个是课程里的老知识，一个是当下的热门技术，最多是“有点像”。真正动手把 KV Cache 切成块、写页表、做 COW 之后才发现，这种相似不是修辞上的，而是结构上的——序列增长对应堆增长，块表对应页表，共享前缀对应共享页，换出对应 swap，抢占对应时间片轮转。一旦接受了这个视角，很多原本觉得“玄学”的推理优化问题就变成了有标准答案的系统问题：显存不够就考虑分页与换出，GPU 空转就考虑批处理与补位，长请求拖慢短请求就考虑抢占与公平份额，权重加载慢就考虑预取与双缓冲。我们最大的收获，是学会把“性能不好”拆成“哪一层、哪个资源、哪条路径”的问题。

第二个体会是关于“可比性”的。项目初期我们犯过一个很典型的错误：E1 的基线和优化组用了不同的分配器参数，结果“分页更好”这个结论其实混杂了多个变量。后来我们把两组收敛到同一份实现、只允许一个开关不同，并把配置摘要写进每次运行的结果里，问题才真正解决。这件事让我们意识到，实验设计里最贵的不是写代码，而是保证“只改了一个东西”。同样的教训还出现在 FAIR 的两套份额账本上：调度器按 token 数排序、MPS 按累计时间选举，看起来都在“按份额”，实际两边对不上，3:1 的配置跑出来接近 1:1。把两个账本合并到同一个 `share` 之后，E10 才出现严格的 0.60/0.20。这些坑如果不亲手踩，是很难从论文里读出来的。

第三个体会是关于“负结果”的价值。E1 的碎片率上升曾让我们很纠结：方案文档写的是“碎片显著下降”，实测却是上升。最初的反应是想换一个指标，比如只报利用率；但我们最终选择保留原指标并解释原因——按块分配天然有块内碎片，空闲链也更分散，分页的收益本来就不在碎片上，而在“按需增长”消除了按最大长度预占导致的 OOM。把这句话写进报告之后，反而有不少同学来问“那什么时候该用分页”，这说明一个诚实的负结果比一个漂亮的正结果更能引发思考。我们也因此形成了一个习惯：每次得到一个“符合预期”的结论，都要反问一句“有没有可能是指标选得巧”。

第四个体会是关于工程约束的。最初为了“像真的并发”，我们用线程加 sleep，结果同一 seed 两次运行结果不同，A/B 对照直接失效。改成单线程事件堆之后，代码反而更短、更清晰：所有延迟都是 `schedule(delay, fn)`，所有并发都是“在同一个时刻注册多个回调”。后来补 `decode_step` 协程时也遇到同样的诱惑——用 `asyncio.sleep` 最省事，但那等于把可复现性交给调度器。最终的做法是先把 DMA 完成时刻算出来入堆，再 await 一个只解包时间戳的句柄，既满足协程契约，又不产生真实挂起。这让我们理解了“接口形式”和“执行语义”是两件事：可以为了契约写成 async，但不能为了省事真的去睡。

第五个体会是关于协作与评审的。两个人做项目，最容易出现的问题是“各写各的，最后拼不起来”。我们的做法是先冻结接口与配置，再并行开发；每完成一个模块就交叉评审，14 轮评审里打回了 7 次，多数问题不是功能缺失，而是命名不一致、异常没有回滚、指标口径不同。比如分页分配失败时忘记归还已拿到的块，单测能过，但会让 OOM 率偏低；再比如 stall 与 compute 重复计时，曲线看起来“更好”，其实是算错了。这些打回让我们养成了一个习惯：提交前先问“这个数字别人能不能复现、这个异常路径有没有人测过”。

最后是对“演示”的理解。我们原本以为报告写完就结束了，直到第一次完整走答辩流程，才发现从打开页面到讲清一个结论，中间有大量细节会打断节奏：旧结果没清空、点到别的实验、图表没有数值、历史记录找不到。后来我们把这些都做进了评测台：一键跑四组、运行期间锁定导航、切换自动清空、悬浮显示数值、历史可筛选收藏。这个过程让我们意识到，工程交付的最后一公里不是“能跑”，而是“别人能在几分钟内看懂并相信”。这也回到本次实习的主题：操作系统讲究的是把复杂隐藏在清晰的接口之后，一个好的演示，本质上也是一次成功的接口设计。

分工遵循“按子系统切分、按接口汇合”的原则：两人各自拥有完整的模块所有权（从设计、实现到测试），但任何跨模块改动都必须经过对方评审。具体协作机制如下：

**（1）接口先行。** 开工第一周先把 `BlockAllocator`、`PageTable`、`Scheduler`、`PrefetchRuntime`、`GPUVMM`、`QuotaManager` 的签名与异常语义写进设计文档并冻结，之后各自实现，互不阻塞。

**（2）交叉评审。** 共进行 14 轮互审，累计打回 7 次，问题集中在三类：失败路径未回滚（分配失败泄漏块）、指标口径不一致（stall 与 compute 重复计时）、命名与配置源不一致（FAIR 与 MPS 两套份额）。每次打回都要求在测试中补一条用例，避免同类问题复发。

**（3）结果只认 JSON。** 报告、图表、答辩脚本中的所有数字都必须能追溯到 `backend/results/*.json` 或 `gpu_results/*.json`，禁止口头传数或手抄。发现口径不一致时，以 JSON 为准回改文档，而不是反过来。

**（4）贡献评分。** 两人自评与互评均为 50%，依据是模块所有权（各占一半子系统）、代码量与实际提交、评审记录与问题修复数量。组长额外承担统稿与答辩组织，组员额外承担测试与真机环境搭建，两项相互抵消，故最终按 50/50 计。
