## 摘要

随着大语言模型（LLM）在在线服务中的规模化部署，推理系统的成本瓶颈已从单次算子性能转移到显存管理、请求调度与数据搬运等系统层面。大模型推理的 KV Cache 具有"按序列增长、可共享、可换出"的特征，与操作系统中的分页内存、写时复制、进程调度和虚拟内存高度同构。本实践以操作系统视角重新审视大模型推理，设计并实现了一套名为 llmOS 的推理操作系统原型：以离散事件时钟统一驱动 KV 内存管理、批处理调度、分层预取与 GPU 虚拟化四个子系统，通过冻结的接口契约与统一的请求状态机串联成一条完整的推理路径，并构建了包含 13 组对照实验的量化评测台与可视化界面。实验结果表明：分页式 KV 管理将 OOM 率由 45.5% 降至 0、峰值并发由 2 提升至 6；持续批处理使吞吐提升 17.1%、首 token 延迟下降 35.4%；分层预取将 DMA 停顿占比由 93.5% 降至 81.7%，有效算力占比提升近三倍；GPU 超卖在保证越界拦截率 100% 的前提下获得 2.5 倍租户密度。全部结果由固定随机种子与黄金 trace 保证可复现，测试覆盖率 93.27%。此外，借助本地部署的 Qwen2.5-0.5B 完成了真实 GPU 上的方向性背书，验证了仿真结论与真实引擎一致。

**关键词**：大模型推理；操作系统；KV Cache 分页；连续批处理；异步预取；GPU 虚拟化

## ABSTRACT

With the large-scale deployment of Large Language Models (LLMs) in online services, the cost bottleneck of inference systems has shifted from single-operator performance to system-level concerns such as memory management, request scheduling, and data movement. The KV Cache of LLM inference grows per sequence, can be shared, and can be swapped out, which is highly isomorphic to paging, copy-on-write, process scheduling, and virtual memory in operating systems. This practice re-examines LLM inference from an OS perspective and implements a prototype inference operating system named llmOS: a discrete-event clock uniformly drives four subsystems — KV memory management, batching and scheduling, hierarchical prefetching, and GPU virtualization — which are connected into a complete inference path through frozen interface contracts and a unified request state machine. A quantitative evaluation bench with 13 controlled experiments and a visualization console is built. Results show that paged KV management reduces the OOM ratio from 45.5% to 0 and raises peak concurrency from 2 to 6; continuous batching improves throughput by 17.1% and reduces TTFT by 35.4%; hierarchical prefetching lowers the DMA stall ratio from 93.5% to 81.7% and nearly triples effective compute utilization; GPU oversubscription achieves 2.5× tenant density while keeping the isolation-violation interception rate at 100%. All results are reproducible under a fixed random seed and a golden trace, with 93.27% test coverage. A local Qwen2.5-0.5B deployment further provides a real-GPU directional backing consistent with the simulation.

**Key words**: Large Language Model Inference; Operating System; KV Cache Paging; Continuous Batching; Asynchronous Prefetching; GPU Virtualization

## 1 绪论

### 1.1 背景与趋势

大模型推理服务的成本结构正在发生变化。以自回归生成为例，每生成一个 token 都要对历史上下文做一次注意力计算，而历史键值（KV Cache）随序列长度线性增长。在 4K 上下文、多并发场景下，KV Cache 的显存占用往往超过模型权重本身，成为限制并发数的第一因素。与此同时，在线服务的请求长度高度不均，静态批处理会让短请求等待长请求，造成 GPU 空转。

这些问题在操作系统课程中都有对应物：显存碎片对应外部碎片，KV 块的共享对应写时复制，请求排队对应进程调度，分层预取对应虚拟内存的按需调页与预读。因此本实践不追求实现一个新的推理引擎，而是把操作系统机制抽取出来，在可控的仿真环境中做定量验证，回答"这些机制在 LLM 负载下究竟能带来多少收益、代价是什么"。

### 1.2 操作系统视角的映射

| 操作系统概念 | 大模型推理中的对应 | 本实践中的实现与验证 |
| --- | --- | --- |
| 分页内存 / 页表 | KV Cache 按块分配、逻辑位置映射物理块 | `BlockAllocator` + `PageTable`，实验 E1/E2/E3 |
| 写时复制（COW） | 相同前缀的 KV 块共享，分叉时再复制 | `fork()` + 引用计数，实验 E2 |
| 进程调度 / 时间片 | 请求批处理、抢占、公平份额 | `StaticBatcher` / `ContinuousBatcher` / `MPSScheduler`，实验 E4/E5/E6 |
| 异步 I/O 与预读 | 权重分层加载、双缓冲、lookahead 预取 | `PrefetchRuntime`，实验 E7 |
| 虚拟内存 / 换页 | GPU 显存超卖、balloon 回收、脏页换出 | `GPUVMM` + VMM pin/unpin，实验 E9 |

### 1.3 实践任务与验收标准

本实践需要交付四个可独立验证的子系统，并保证它们在同一个时钟下协同工作：

1. **KV 内存管理**：分页分配、COW 前缀共享、LRU 换出，相对连续预占必须降低 OOM。
2. **批处理调度**：静态批与持续批共用同一代价函数，公平调度使多租户 P99 方差下降。
3. **分层预取与异步 I/O**：串行、双缓冲、预取+缓存三级对比，停顿占比单调下降。
4. **GPU 虚拟化**：逻辑页可超过物理页，越界拦截率必须为 0，并给出超卖比–延迟 Pareto 曲线。

评测侧要求全部实验为"同一 seed、同一负载、只改一个机制"的 A/B 对照，配置参数冻结（seed=42、block_size=16、num_kv_blocks=1024、prefill 2×10⁻⁵ s/token、decode 1×10⁻³ s/step、三级带宽 3.5/16/800 GB/s），结果需可一键复现。

## 2 预备实验

### 2.1 实验环境

实验在 Windows 11 上完成，使用 Python 3.12.10，内核仅依赖标准库（`heapq` 事件堆、`dataclasses`、`random`），评测脚本使用 matplotlib 出图。整个仿真阶段不需要 GPU；真实 GPU 背书可选，使用 NVIDIA RTX 5060（8GB）、PyTorch 2.8.0+cu128、transformers 5.3.0 与本地 Qwen2.5-0.5B 权重。

选择标准库而非 simpy，是为了让"离散事件不依赖线程调度、禁止真实 sleep"成为结构性保证；所有等待都表示为事件堆中的完成时刻，随机数只来自 `random.Random(seed)`。

### 2.2 实验一：内存管理——连续预占 vs 分页（E1）

**目的**：验证分页式 KV 管理相对连续预占是否能降低 OOM、提高并发。

**方法**：负载为泊松到达的 11 条请求，prompt 长度 2048–4096、生成长度 256–512，KV 池 1024 块、每块 16 token。基线按 `prompt+gen` 一次性预留连续块且不做换出；优化侧按需逐块分配，满池抛 `AllocError`。

**结果**：

| 指标 | 连续预占（基线） | 分页（优化） |
| --- | --- | --- |
| OOM 率 | 45.45% | 0 |
| 峰值并发 | 2 | 6 |
| 活跃序列峰值 | 1 | 6 |
| KV 池利用率峰值 | 72.3% | 99.9% |
| 碎片峰值 | 16.0% | 46.9% |
| 吞吐（req/s） | 2.74 | 2.17 |
| 换出次数 | 0 | 812 |

**分析**：连续预占的失败源于"按最大长度预留"，短请求也占用长请求的空间；分页把分配粒度降到 16 token，使同样的池子容纳三倍并发，OOM 清零。代价有两项：一是按块分配产生块内碎片，碎片峰值反而升高；二是频繁换出使吞吐下降 20.9%。这说明分页的收益不是"所有指标都变好"，而是用吞吐与碎片换取了可用性与并发。

### 2.3 实验二：任务调度——静态批 vs 持续批（E4）

**目的**：验证持续批处理相对静态批处理能否提高吞吐、降低首 token 延迟。

**方法**：两种调度器共用同一请求推进函数与代价模型（prefill 按 token 线性、decode 按 batch 线性），批大小上限 8，仅改变"何时换批"的策略。静态批等待整批结束；持续批完成即离队、空槽立即补入。

**结果**：

| 指标 | 静态批（基线） | 持续批（优化） |
| --- | --- | --- |
| 吞吐（req/s） | 10.10 | 11.83（+17.1%） |
| GPU 忙闲比 | 95.2% | 98.9% |
| TTFT P50（s） | 1.043 | 0.674（−35.4%） |
| TTFT P99（s） | 1.043 | 0.674 |

**分析**：静态批的尾部空泡来自"一批中最长请求决定整批结束时间"，持续批把空泡填满，同时让短请求不必排队等待，因此首 token 延迟显著下降。这是后续公平调度实验（E6）的基础。

### 2.4 预备实验小结

两项预备实验对应任务书要求的"内存管理实验"与"任务调度实验"，验证了 OS 机制在 LLM 负载下的可迁移性。实验代码位于 `backend/llmos/`，可通过 `python -m pytest` 与 `python scripts/run_ab.py` 一键复现；当时已建立 46 项测试、覆盖率 93.27% 的回归基线。

## 3 场景项目：llmOS 推理操作系统

### 3.1 场景背景与需求

场景设定为一个多租户在线推理服务：两个租户共享一张 GPU，分别承载交互式对话（低延迟敏感）与批量摘要（吞吐敏感）。服务需要满足：

| 需求 | 指标 | 验收方式 |
| --- | --- | --- |
| 不因显存碎片失败 | OOM 率 = 0 | E1/E3/E11 |
| 交互体验 | TTFT P50 ≤ 1 s | E4/E5 |
| 多租户公平 | 跨租户 P99 方差显著下降、无长期饥饿 | E6 |
| 权重加载不阻塞计算 | DMA 停顿占比单调下降 | E7 |
| 隔离与配额 | 越界拦截率 100%、超额申请被拒 | E8/E9 |
| 可复现 | 固定 seed 下指标波动 ≤ 1% | 黄金 trace 回归 |

### 3.2 系统设计

#### 3.2.1 总体架构

llmOS 采用"单时钟 + 四子系统 + 冻结契约"的结构。`DiscreteEventSim` 用最小堆维护事件，所有子系统只通过 `schedule(delay, callback)` 推进时间，不存在真实线程与睡眠。一条请求的生命周期为：到达 → 准入（配额）→ 排队（调度）→ 分配 KV 块（内存/页表）→ 每拍前向（预取 stall 计入）→ 完成释放；若显存不足则触发换出或 `AllocError`，若访问越界则触发 `IsolationError`。

四个子系统之间只依赖接口，不依赖彼此内部状态：调度器不知道页表实现，预取器不知道调度策略，VMM 只暴露 `create_tenant/access/balloon_reclaim`。这一约束由模块图和代码审查清单保证。

#### 3.2.2 KV 内存管理

`BlockAllocator` 维护空闲块栈与引用计数，`PageTable` 维护每条序列的逻辑块表。`fork()` 对共享块加引用而不复制，实现 COW；`free()` 仅在引用计数归零时归还块，避免提前回收共享块；`steal_for_eviction()` 只允许驱逐引用计数为 1 的块，否则必须先分裂。碎片率定义为空闲块的分散程度，利用率定义为已用块占池比例。

配额层按 `ceil((prompt+gen)/16) × 每块 GB` 做块粒度预留，避免按 token 计费导致的超额准入；硬上限触发 `QuotaOOM`，由调度器捕获并拒绝请求。

#### 3.2.3 批处理调度

调度器共享基类与代价函数：prefill 代价 `α × prompt_len`，decode 代价 `β × batch`。静态批攒满一批或超时后整体执行；持续批每拍回收已完成槽位并补入新请求。SJF 按剩余长度排序，抢占式调度在长请求占用时间片后将其挂起，饥饿检测按"等待时间超过最短作业时间的 10 倍"判定。公平调度（FAIR）把 MPS 时间片与租户份额绑定，按份额加权选择下一个租户，只对时间片窗口记账而不做排他占用。

#### 3.2.4 分层预取与异步 I/O

权重按层组织，`PrefetchRuntime` 维护当前层与 lookahead 窗口。串行模式逐层同步加载；双缓冲在计算第 i 层时搬运第 i+1 层；预取+缓存进一步复用已加载层，减少重复 DMA。停顿定义为"本拍等待数据的时间"，DMA 忙碌本身不计入 GPU 有效算力。`decode_step(layer)` 以协程形式暴露接口，把 await 点翻译为事件完成回调，因此接口符合异步语义但不产生真实挂起。

#### 3.2.5 GPU 虚拟化

`GPUVMM` 为每个租户建立独立的客户物理页到宿主物理页映射，物理页数小于逻辑页数即构成超卖。访问越界或映射缺失时抛出 `IsolationError` 并计入拦截统计。balloon 回收按租户压力选择冷页，脏页换出需计入 `swap_write_delay`。评测侧输出"超卖比–虚拟化延迟"曲线与越界拦截率、隔离违规率。

#### 3.2.6 评测台与可复现性

后端以 FastAPI 暴露实验目录、运行接口与历史记录，结果落 SQLite；每次运行携带 `config_digest` 与 seed。前端为 Vue 3 单页评测台，左侧按四任务分组选择实验，右侧展示结论条、基线/优化指标对照卡、折线/柱状/Pareto/热力图、基线/优化并排甘特、消融热力图与原始 JSON，并支持历史回放与深链（`?exp=E1&seed=42&run=29`）。

### 3.4 测试与评测

#### 3.4.1 测试策略

测试分三层：单元测试覆盖分配器引用计数、页表越界、COW 分裂、换出选择、配额粒度、VMM 越界与 balloon；契约测试验证冻结接口签名与异常语义；端到端测试跑固定 seed 的黄金 trace，指标波动超过 1% 即判定回归。当前共 46 项测试全部通过，语句覆盖率 93.27%，高于 70% 的门禁。

| E13 | 2 租户 vs 8 租户 | 公平指数 0.997 → 0.896，吞吐持平 |

#### 3.4.3 真实 GPU 方向背书

为避免"纯仿真"的说服力不足，使用本地 Qwen2.5-0.5B（FP16）在 RTX 5060 上做了 G1 对照：基线按最大长度预占 KV（`StaticCache`），优化侧按需增长（`DynamicCache`），并发从 64 扫到 640。基线在 192 并发时触及 7.72 GB 显存上限并 OOM，按需分配可承载 640 并发（7.75 GB），承载能力提升 3.33 倍，方向与仿真 E1 一致。另测得该模型 KV 为 12,288 B/token，与理论公式（2 × 24 层 × 2 KV 头 × 64 维 × 2 字节）完全吻合。

需要说明的是，参数校准结果（prefill 约 2.5 ms 固定开销 + 0.122 ms/token，decode 约 29.5 ms/步且对 batch 不敏感）与仿真冻结常数存在数量级差异。原因是冻结常数刻画的是数十 B 级 GQA 模型在数据中心 GPU 上的行为，而 0.5B 模型在桌面卡上受内核发射开销主导。该结果仅作为灵敏度附录，不回写冻结配置，也不参与主评测。

#### 3.4.4 典型结果分析

**E7 的消融**：4×4 网格（lookahead × 缓存层数）显示，lookahead 从 1 增到 2 的收益有限，而缓存层数从 0 增到 11 时停顿占比出现阶跃式下降。这说明在权重分层加载场景中，"复用已加载层"比"提前更多层"更有效，因为重复 DMA 才是停顿的主要来源。

**E6 的公平性**：FCFS 下两个租户的 P99 相差数倍，FAIR 后柱状图基本拉平，方差下降 85%，而吞吐只损失 0.9%。E10 进一步验证份额可调：配置 3:1 后累计服务时间比为 0.60:0.20，Jain 指数保持 1.00。

**E9 的 Pareto 曲线**：虚拟化延迟随超卖比单调上升（1.0× 时 0.47 s，2.5× 时 1.47 s），同时越界拦截率保持 100%。这条曲线给出了"密度–延迟"的显式权衡，可直接用于容量规划。

### 3.5 创新点

1. **统一时钟下的跨子系统联动**：13 组实验共用同一请求状态机与代价函数，避免了"四个互不相通的脚本"。
2. **冻结契约与错误语义**：接口签名、配置常数、异常类型全部冻结，任何机制改动都必须通过黄金 trace 回归，保证对比公平。
3. **可解释的消融**：不仅给出"优化更好"，还通过 lookahead × 缓存层数的 4×4 网格定位收益来源。
4. **真实 GPU 与仿真解耦**：真机背书走独立适配器与独立结果目录，既不污染仿真数字，又提供了方向性证据。
5. **可视化评测台**：把指标对照、图表、甘特、消融、历史回放整合为一个可演示、可深链的界面，答辩时无需额外准备材料。

### 3.6 不足与改进方向

1. **碎片指标未达预期**：E1 的碎片峰值反而上升，收益主要体现在 OOM 与并发。后续可改用"最大连续空闲块占比"作为外部碎片指标，并评估块大小自适应。
2. **异步接口为薄封装**：`decode_step` 保留了协程签名，但内部直接翻译为事件回调，未真正使用 asyncio 事件循环；若评审强调接口一致性，可补一层事件循环适配。
3. **真实负载覆盖不足**：目前以合成泊松负载为主，尚未接入 ShareGPT / Azure trace 的完整离线 tokenize 流程。
4. **真机对照仅一项**：G2（持续批 vs 静态批，对应 E4）需要 vLLM，受 Windows 环境限制未完成，可在云端 GPU 补充。

## 4 心得体会

本次实践最大的收获是"换一个视角看同一个问题"。在接触这个题目之前，我们对大模型推理的理解停留在"模型多大、卡多快"；真正动手做仿真之后才发现，同样的模型和同样的卡，仅改变 KV 的分配方式和请求的排队策略，吞吐与延迟就能相差数十个百分点。操作系统课上学的分页、写时复制、时间片、按需调页，在这里不是抽象概念，而是可以直接换算成 OOM 率和 P99 的具体机制。

第二个收获是"可复现"的工程价值。我们最初也出现过指标对不上的情况：改了一处换出逻辑，E7 的结论就反了；换一个 seed，E6 的方差又不降了。正是被这些问题逼着建立了固定 seed、黄金 trace、双列输出和覆盖率门禁，才让后面的每一个结论都站得住。相比"跑出一个好看的数字"，能解释这个数字从哪来、在什么条件下成立，才是系统类工作更重要的部分。

第三个收获来自真实 GPU 的那次对照。仿真里 OOM 是一个计数器，真机上则是实实在在的显存耗尽与进程报错；也正是在真机上，我们才直观看到"连续预占先撞墙、按需分配能多跑三倍"这一结论并不是仿真的 artifact。虽然 0.5B 模型的绝对耗时与仿真常数差了一个数量级，但这种"方向一致、量级可解释"的结果，反而让我们更清楚仿真能回答什么、不能回答什么。

最后是协作层面的体会。两个人分别负责架构与内存、运行时 IO 与测试，接口一旦冻结，改动就必须走交叉评审。互审记录里那些被打回的条目——引用计数未检查、两套份额来源、stall 把 DMA 忙碌算进去——每一条都对应一次真实的返工，也让我们理解了"契约"二字在系统项目里的分量。
